驱动方式修正了，
但漏液还没有修好

新版不再逐帧瞬移杯子，而是让 PhysX 用 kinematic target 正规驱动，并用跟随相机保留完整动作。结果很明确：两条 1589 帧视频已经重录，真实产图约 42 FPS；杯外散粒和穿透仍可见，因此性能与液体质量都暂时是 NO-GO。

3 分钟电梯版（面试可直接讲）

我遇到的是一个指标合同错位：GUI overlay 显示约 50 FPS，同事录屏也很流畅，但同步 headless RGB 端点只有 3.31 FPS。overlay 测的是 viewport 更新，不证明每秒真的有 50 张模型能消费的新 RTX 图。

我把物理和渲染拆成 30/50 两个时钟，用目标 render product 的 NEW_FRAME 完成事件计数；每一帧都必须有递增 frame number，并通过 LdrColor(device="cuda") 进入三槽 GPU consumer。计时路径不做 CPU RGB 读回。

历史 teleport + 固定相机链路在 fast-glass 下曾达到 52.22 / 51.85 FPS，但那条视频的杯子驱动不规范、后半程还被裁掉，不能代表现在的方法。新版使用 PhysX kinematic target 和跟随构图，六次资格运行均只有约 41–42 FPS。

这次完整视频没有藏失败：两个杯子全程在画面里，液体却会形成脱离杯体的团块和细长穿透痕迹。它适合说明问题，不适合证明“不撒不漏”，更不能当作 50 Hz 实时数采已闭合。

02 · The misleading number

GUI 写着 50，MP4 却只有 30

同事给的 GUI 视频是 1554×1068、504 帧、16.8 秒，文件编码帧率是 30 FPS。角落 overlay 显示约 49.76–54.16 FPS，那更接近编辑器 viewport 的刷新/应用循环速度。

而最初正式模型端点要求每个物理步都等待 RTX 完成、把 1554×1068 RGB 从 GPU 读回 CPU。它测到 301.88 ms/帧，也就是 3.31 FPS。两个数字都可能是真的，只是回答了不同问题。

50-ishGUI overlay · 非完成帧证据
30 FPS同事 MP4 的实际编码率
3.31 FPS1554×1068 同步 CPU RGB
≈42 FPS新版 kinematic + 跟随相机实测

先定义“什么才算交付了一帧”，再谈 FPS。否则大家只是拿同一个单位讲四件不同的事。

03 · Frame completion contract

什么才算一张新图

target render product emits NEW_FRAME
  → product_path matches
  → frame_number strictly increases
  → LdrColor is a CUDA tensor
  → copy into GPU ring / full-frame store
  → CUDA event completes
  → count exactly one delivered frame

不能数 app.update()，因为一次 update 未必完成一张新图；也不能只看 annotator 指针，因为 Isaac 4.1 偶尔会在事件边界给出未注册的 host pointer。我们丢弃这类无效事件，继续等待下一张真正 CUDA 图，并把丢弃次数写入证据。

为什么是 1589 帧？

轨迹有 953 个 30 Hz 物理状态。目标渲染频率是 50 Hz：

render_count = ceil(953 × 50 / 30) = 1589
physics_index = floor(render_index × 30 / 50)

因此每个物理状态至少出现一次；约 2/5 的物理状态会支持第二张新 RTX 图。这不是把旧像素重复发两遍，而是同一状态的两次新渲染完成。

04 · The debugging campaign

四幕排障：速度不是唯一门

  1. 第一幕：把同步大端点拆开。 物理约 6–10 ms，真正拖慢 1554×1068 路线的是 RTX 完成和 CPU 读回。我们改为 256×256、GPU 常驻、30/50 双时钟。
  2. 第二幕：57 FPS 的假胜利。 fast-opaque 关闭透明路径后很快，但视觉复核只看到一团青色液体，玻璃烧杯消失。性能通过、任务画面失败，候选被拒绝。
  3. 第三幕：用画面反推最小光照集合。 原始玻璃清楚但贴着 50 波动。关 TAA 反而更慢，因为 op=3 是 DLSS 快路径；折射降到 1 次杯壁消失，2 次仍可辨。最终保留 DLSS、反射、阴影、透明，关闭间接漫反射。
  4. 第四幕：把单次成功升级成资格。 原始玻璃在 headless/offscreen 都只有 1/3 过线；fast-glass 两边都是 3/3。期间还抓到一次配置分支覆盖错误和一次 GPU 利用率残留误报，说明 effective settings 和重复实验比 profile 名字可靠。
我最大的一次误判

第一次完整 fast-glass 跑到 55.19 FPS，我差点把它当成最终结果；结果 effective settings 证明它实际生效的是 1 次折射，杯壁已经消失。证据字段救了结论。

05.5 · 2026-08-13 kinematic follow-up

把“拖动杯子”改规范以后，漏液并没有自动消失

旧视频的问题不是杯子真的被机械手稳定拿住，而是每个 30 Hz 控制点直接改 USD transform，再要求 PhysX 接受一次瞬移。新实现把源杯改成 kinematic rigid body，用 RigidBodyView.set_kinematic_targets 写入目标；30 Hz 控制点之间按 30/60/120 Hz 插值，并在每次写入后读取 PhysX 的真实姿态。

这组数字把两个问题拆开了：杯子驱动已经修好，但液体仍在尚未倾斜时从 548/548 下降到约 524–526 个杯内。更小的 120 Hz 步长没有救回质量，最终穿到桌下的粒子反而从 1 个增加到 30 个。因此根因不再是“轨迹瞬移”，而应继续查粒子初始间距、源杯 convex decomposition 内壁、rest/contact offset 与运动碰撞裕量。

为什么现在有新视频，但仍然写 NO-GO

我们后来明确选择“质量不过也先比较速度”，所以越过原 stop rule，额外产出了诊断视频。两条完整运行最终分别有 503/504 个粒子到目标杯，43/42 个落在桌面，另各有 2 个落到桌下；目标接收率超过 91%，但稳定尾段、撒漏和穿透门仍失败。视频是对失败的可视化，不是验收通过。

06 · Evidence boundary

知道哪条线闭合，比“全都成功”更重要

已闭合

  • 每张图由目标 RTX NEW_FRAME 事件证明完成。
  • 1589 张图严格递增并进入 CUDA consumer。
  • 新版两个杯子在完整动作里保持可见，不再发生旧视频的后半程裁切。
  • 两条新版运行均绑定 Isaac 4.1 effective-runtime v2 receipt。
  • 源杯已改为 PhysX kinematic target，姿态读回误差远低于 0.5 mm / 0.1° 门槛。

未闭合

  • 新版资格矩阵六次均未达到 50 RTX FPS 或 30 Hz 物理。
  • 完整视频最终仍有 42–43 个粒子撒在桌面、各 2 个粒子落到桌下。
  • 本地视觉复核看到脱离杯体的团块与细线状穿透。
  • H.264 是按 50 FPS 编码播放，不代表实时产图达到 50 FPS。
  • 尚未接真实模型队列，不声称端到端模型吞吐。
正确对外表述

“我们已经用规范 kinematic 驱动重录完整诊断视频；当前单相机 256×256 RTX 实际约 42 FPS，视频按 50 FPS 播放，液体撒漏与穿透仍未通过。”

07 · Future evaluation input

能输出给评测吗？能，但先别偷换语义

这条链路已经能够输出标准 50 FPS 播放的 MP4，也能输出逐帧图像或 CUDA tensor 流，所以技术上可以作为未来评测的相机帧源。但当前真实在线吞吐约 42 FPS，不能对评测方承诺稳定 50 Hz 实时输入。模型/动作通常按 30 Hz 决策时，可以在每个决策点取“最新且因果有效”的一张图。

真正接评测时再补三件事：每帧双时间戳（物理 sim time 与 RTX 完成 wall time）、frame→physics/action 映射、模型积压时的 latest-frame/drop 记录。本项目现在没有修改 EOS，也没有把 GPU checksum 假消费者冒充成模型。

08 · Interview follow-ups

面试官大概率会追问什么

GUI 都显示 50 FPS 了，为什么还要重测？

因为 overlay 没有证明目标相机完成了新 RTX 图，也没有证明图像进入模型可用的 tensor。完成事件、递增帧号和消费者是三个独立门。

为什么不直接关掉玻璃透明，速度不是更快吗？

fast-opaque 确实更快，但烧杯从 observation 中消失，属于任务语义破坏。最终配置是视觉可辨与吞吐之间的最小妥协，不是最高裸 FPS。

MP4 属性写着 50 FPS，为什么结果还不算 50 Hz？

MP4 的 50 FPS 决定播放器用多快的节奏展示 1589 张图；真实吞吐看计时窗口生成这些图用了多久。新版两条视频分别只有 42.83 / 41.99 FPS，所以播放会比生产时的墙钟更快。

为什么 3 次都要跑？

原始玻璃最能说明问题：单次曾有 50.36，但另外两次 47.65/48.92。没有重复资格，就很容易挑到一次幸运结果。

最值得复用的方法是什么？

先定义可证伪的端点，再分层测量；所有优化都记录 effective settings；速度门与视觉/物理质量门分开；单次成功永远不自动升级为资格声明。

改成 kinematic target 后为什么还漏？

kinematic target 修复的是“杯子怎么移动”，不是“粒子和杯壁如何接触”。姿态回读已经证明杯子严格跟轨迹走；剩余的早期漏液更指向源杯内壁碰撞近似、offset 和粒子初始状态。把积分从 30 提高到 120 Hz 仍失败，也排除了“只要多算几个子步就好”的简单解释。
